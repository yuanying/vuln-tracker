# 0012. vuln-responder の直しは、マージされたらすぐパッチ版にする

- Date: 2026-10-28
- Status: Accepted

## Context

vuln-responder（fraction-agents の係）は、脆弱性の直しを自作イメージのソースのリポジトリに PR として出す。ユーザーがその PR をマージしても、直しがイメージの版になるのは、人が `v*` のタグを打つか、週次のリリース（ADR 0010）が動いたときだった。週次は Renovate のコミットしか数えないので、係のコミットが入れば週次も止まる。直したのに本番に届かない時間が、最長で 1 週間を超えて伸びる。

直しの流れは、マージ → 次のパッチ版 → 集計役が `fixed-in-release` を見て係に再依頼 → 係が fleet-infra に版上げの PR、とつながる（vuln-tracker の契約 E。fraction-vuln-tracking のタスクで全自作リポジトリに同じ規則を入れる）。最初の段がリリースを待てば、残りもすべて待つ。

一方で、ADR 0010 の「人が書いた変更を機械がリリースしない」は崩さない。係はタグを打たない。タグは CI が打つ。

## Decision

### 係のブランチの PR がマージされたら、すぐ同じ判定でリリースする

`release` のワークフローに、main への PR が閉じられたとき（`pull_request` の `closed`）のきっかけを足す。次のすべてを満たすときだけ、週次と同じ判定（`hack/release-plan`）を走らせる。

| 条件 | 理由 |
|---|---|
| マージされた（`merged` が真） | マージされずに閉じた PR は main に何も入れていない |
| head のブランチが `vuln-responder/` で始まる | 係のブランチの命名。Renovate の PR や人の PR では動かない |
| head のリポジトリがこのリポジトリ自身 | fork のブランチ名を真似ても動かない |

判定はマージコミットそのものについて行い、イメージもタグもそのコミットに付ける。マージの後に main に入った別のコミットは含めない。人のコミットが後から入っても、直しのリリースを止めないためである。

### 係のコミットを Renovate のコミットと同じに数える

判定の 1 つ目の条件（ADR 0010）を広げる。最新の版タグ以降のマージ以外のコミットの作者が、すべて `renovate[bot]` か `fraction-vuln-responder[bot]` であること。後者は係の GitHub App の bot の名前で、係はこの名前とメール（`348762456+fraction-vuln-responder[bot]@users.noreply.github.com`）でコミットする。比べるのは git に残る作者の名前で、Renovate と同じ扱いである。似た名前（`vuln-responder[bot]` など）は人として数える。

この広げ方は週次にも効く。すぐのリリースが失敗しても、次の週次が同じコミットを出す。2 つ目の条件（イメージの中身が変わっていること）は変えない。

係のコミットを含む版のタグのメッセージは、1 行目を「脆弱性の直しと依存の更新」にし、本文にコミットの件名を並べる。Renovate だけの版は、これまでどおり「依存の更新」である。

### 人のコミットで止まったら、何が止めたかと手で出す方法を残す

人のコミットが 1 つでもあれば、すぐのリリースも週次も出さない（ADR 0010 のまま）。そのときは実行の job summary に、止めたコミット（短い hash・件名・作者）の一覧と、そのコミットに手で版タグを打って push するコマンドを書く。人がタグを push すれば、`publish` がそのタグのイメージを出す（ADR 0008）。版は人が選び直してよく、コマンドは次のパッチ版を例として示す。

### 週次と同時に走らせない

すぐのリリースと週次は同じ concurrency のグループで、1 つずつ走る。待っているものは打ち切らない。閉じられた PR はどれもこのワークフローを起動するので、係の PR 以外は PR ごとの別のグループに入れ、待っている本物のリリースの順番を奪わないようにする。

### 権限は今のまま

先頭は読み取りのみで、パッケージへの書き込みは `publish` を呼ぶジョブに、タグを打つ権限はタグのジョブにだけ与える（ADR 0010 と同じ）。`publish` には、打つ予定のコミットを渡す入力を足し、テスト・ビルド・ラベルの `revision` をそのコミットに揃える。

## Consequences

- 係の直しは、ユーザーがマージした数分後にパッチ版になる。本番に入れるのは、これまでどおり fleet-infra の版上げとユーザーの apply である
- 前回の版から人のコミットが入っていると、係の直しも人のリリースを待つ。job summary の一覧とコマンドで、人がすぐ出せる。気付けなかった場合は、fleet-infra の `VulnTrackerFixedButUnreleased`（Critical が 1 時間以上 `fixed-in-main` に留まる）が鳴る
- 閉じられた PR ごとに、何もしない `release` の実行が 1 つ増える
- このリポジトリの作者名の比べ方は、git の作者名を自分で名乗れば通る。ブランチ保護の無いリポジトリで、マージはユーザーが行うので、通っても出るのはユーザーがマージしたものだけである
- 止めたいときは、`release` のワークフローを無効にすればよい。週次も同時に止まる
