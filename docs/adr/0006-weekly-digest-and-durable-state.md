# 0006. 週次ダイジェストを Slack に送り、差分のための状態を ConfigMap に置く

- Date: 2026-10-27
- Status: Accepted

## Context

普段の通知は、週次などのダイジェストにする（grill-me の決定 1）。載せるのは、新しく出たもの・
段階が進んだもの・注釈の期限切れである。Alertmanager にはダイジェストの機能が無いので、
集計役が自分で Slack に送る。

「新しく出た」「段階が進んだ」を言うには、前回のダイジェストの時点の状態が要る。集計役は
レプリカ 1 つで、再起動されることがある。再起動で状態を失うと、次のダイジェストに
すべてが「新しい」として載ってしまう。

## Decision

### 送る時と送り先

- 送る時は設定で決める（既定は毎週月曜 09:00、タイムゾーンは `Asia/Tokyo`）
- 送り先は Slack の Incoming Webhook。URL は Secret から環境変数で受け取る。URL が無ければ
  ダイジェストを送らない（ログに書くだけ）
- 送る時刻に集計役が止まっていたら、起動したときに、前回送った時刻から 7 日以上たっていれば送る
- 送れなかったら、間隔を空けて取り直す。送れた時刻を状態に書いてから次の送る時を待つ

### 中身

| 節 | 中身 |
|---|---|
| 概況 | 段階ごとの件数（重大度は既定 `CRITICAL,HIGH`） |
| 新しく出たもの | 前回のダイジェストの後に初めて見た発見（イメージ・脆弱性・重大度・段階・修正版の有無・注釈） |
| 段階が進んだもの | 前回と比べて段階が先に進んだ発見（前の段階 → 今の段階） |
| 本番で直ったもの | 前回はあったが、今は無い発見の件数（イメージごと） |
| 注釈の期限切れ | 見直す期限を過ぎた注釈（イメージ・脆弱性・state・期限・理由の文） |

- どの節も、ダッシュボードへのリンクを付ける（URL は設定で与える）。注釈には fleet-infra の
  VEX のファイルへのリンクを付ける
- 対象の重大度は、発見ごとのメトリクスと同じ集合（既定 `CRITICAL,HIGH`）にする
- Slack の 1 メッセージに収まらない長さになったら、節ごとに先頭の何件かを載せ、
  残りは件数とダッシュボードへのリンクにする
- 理由の文はメトリクスには出さず（ADR 0004）、ダイジェストにだけ出す

### 状態の置き場

状態は集計役の namespace の ConfigMap 1 つ（既定 `vuln-tracker-state`）に置く。

| 状態 | 中身 |
|---|---|
| 初めて見た時刻 | `image` × `vulnerability_id` → 初めて見た時刻、最後に見た時刻（ADR 0005） |
| 前回のダイジェストの断面 | 対象の重大度の発見ごとの段階と注釈の state |
| 前回送った時刻 | |

- 中身は JSON を gzip で縮めて `binaryData` に入れる。2026-10-27 の本番の量（組 3,908）で、
  縮める前で数百 KB、縮めた後で数十 KB の見込みであり、ConfigMap の上限（1MiB）に余裕がある
- 起動時に読み、変わったら書く（書く頻度は 1 分に 1 回まで）。読み書きは楽観的な並行制御
  （resourceVersion）で行う。レプリカ 1 つかつ `Recreate` なので、衝突はふつう起きない
- ConfigMap は集計役が作る。マニフェストには含めない（中身は集計役だけが書く）

PersistentVolume にしなかったのは、量が小さく、Longhorn のボリュームを 1 つ増やすほどの価値が
無いからである。ConfigMap なら RBAC で書き込み先を 1 つに絞れる。

## Consequences

- 再起動しても「新しい」と「前回からの差分」を失わない
- 集計役が ConfigMap の作成・更新の権限を持つ。権限は集計役の namespace の中だけで、
  名前で 1 つに絞れない作成の権限を除き、読み書きは `resourceNames` で絞る（ADR 0007）
- ConfigMap を消すと、初めて見た時刻が失われる。そのとき見えている組は時刻 0 になり（ADR 0005）、
  次のダイジェストは「新しく出たもの」を空にする
- 送る時に止まっていた場合の取り直しは「前回から 7 日以上」で判断するので、送る時を変えた直後は
  1 回ずれることがある
