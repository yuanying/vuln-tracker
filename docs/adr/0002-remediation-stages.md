# 0002. 対応の段階を、候補の版のスキャンと git から決める

- Date: 2026-10-27
- Status: Accepted

## Context

脆弱性ひとつについて「対応のどこまで進んだか」を出したい。直す流れは、イメージを誰が作るかで
2 通りある。

- **自作のイメージ**（`ghcr.io/yuanying/*` など）: 依存を main で更新する → リリースのタグを打つ →
  fleet-infra（か k8s-manifests-fraction）の版を上げる → 本番に apply する
- **外のイメージ**（Docker Hub・quay.io・registry.k8s.io など）: 上流が新しい版を出す →
  fleet-infra の版を上げる（Renovate の PR が来ることが多い）→ 本番に apply する

どちらも、途中の各点に「その時点の版」がある。自作なら `:main` とリリースのタグ、外なら上流の
同じ系列の新しい版、どちらでも git に書かれた版である。その版をスキャンして脆弱性が消えていれば、
そこまで直っていると言える。

自作のイメージの CI は、既定ブランチへの push ごとに `:main` を出し、イメージのラベルに
`org.opencontainers.image.source` と `org.opencontainers.image.revision` を付ける（契約 B）。

## Decision

### 段階を持つ単位

段階は **発見（finding）** ごとに 1 つ持つ。発見とは、本番で動いている版 1 つ（イメージの
リポジトリ × digest）の中の、脆弱性 1 つ × パッケージ 1 つである。同じ CVE が 1 つのイメージの
2 つのパッケージで出れば、発見は 2 つになる。

「本番で動いている」とは、その digest を使う Pod がクラスタにあることである。
VulnerabilityReport は 0 にスケールされた古い ReplicaSet にも残っている（2026-10-27 に 7 件を確認）ので、
レポートがあるだけでは動いているとは見なさない。CronJob と Job のレポートは、Pod がいない間も
動いているものとして扱う（次の実行でまた動く）。

動いている場所（namespace・ワークロード・コンテナ）は発見の外に持ち、別のメトリクスで結ぶ
（ADR 0005）。同じ版が 3 つのワークロードで動いていても、段階は 1 つである。

レポートは TTL で消えて取り直される。消えてから取り直されるまでの間も、その digest を使う Pod が
あるかぎり、最後に読んだ中身で発見を持ち続ける。

### イメージを分ける: 自作か、外か

イメージの設定（config）のラベル `org.opencontainers.image.source` を読む。その URL が
設定した持ち主（既定 `https://github.com/yuanying/`）の下を指していれば **自作**、そうでなければ
**外** とする。

ラベルが無いイメージは、fleet-infra の対応表（下記）でソースを補う。どちらでもソースが分からなくても、
外のイメージとしての段階の判定（レジストリのタグを読む）はできるので、段階はそのまま決める。
ソースが分からないことは、イメージの情報のメトリクスで `source` が空になることで表し、
ダッシュボードの「対応先不明」の一覧に出す。

### 候補の版

イメージ（のリポジトリ × 動いている digest）ごとに、直っているかもしれない版を候補として集める。

| 候補 | 自作 | 外 | 見つけ方 |
|---|---|---|---|
| `main` | ○ | | 同じリポジトリのタグ `main` の、今の digest |
| `release` | ○ | | レジストリのタグのうち semver で最大のもの（動いている版より新しいときだけ） |
| `upstream` | | ○ | 同じ系列の最新版（下記）。semver でないタグは、同じタグの今の digest が動いている digest と違うとき、その digest |
| `git` | ○ | ○ | fleet-infra と k8s-manifests-fraction の既定ブランチに書かれた、このイメージの版のうち、動いている digest と違うもの |

候補は digest で同一視する。`release` と `git` が同じ digest なら、スキャンは 1 回で済む。
`:main` のラベルの revision が `release` のラベルの revision と同じなら、中身も同じとして
`main` のスキャンを省く。

**同じ系列**: タグを「`v` の有無・数字の版・その後ろの接尾辞」に分け、接尾辞（`-alpine`・
`-distroless` など）が同じで、major が同じで、版が動いている版より新しいもののうち最大のもの。
数字の版が読めないタグ（`latest`・`alpine`）は semver でないタグとして digest の変化で見る。
系列の決め方が合わないイメージは、fleet-infra の対応表でタグの正規表現を与えて上書きできる。

**git に書かれた版**: 両リポジトリのすべての YAML を読み、次の形でこのイメージの名前と版を見つける。
kustomization の `images`（`name` / `newName` と `newTag`、`newTag` の `tag@digest` の形を含む）、
`image:` に書かれた参照、Helm の values の `repository` と `tag` の組。名前は Trivy と同じに正規化する
（Docker Hub は `index.docker.io`、公式イメージは `library/`）。テンプレートの中で組み立てる形など、
これで見つからない書き方は見つからない（段階が `git` まで進まない）。

### 段階

発見の段階は、候補のうちその脆弱性（同じ ID・同じパッケージ名）が **消えている** ものの中で、
最も先に進んだものから決める。

| 段階 | 自作 | 外 | 意味 |
|---|---|---|---|
| `in-git` | ○ | ○ | git に書かれた版では消えている。本番に未反映 |
| `fixed-in-release` | ○ | | リリースのタグでは消えている。git は古い版のまま |
| `fixed-upstream` | | ○ | 上流の同じ系列の新しい版では消えている。git は古い版のまま |
| `fixed-in-main` | ○ | | `:main` では消えている。リリース未 |
| `unfixed` | ○ | ○ | どの候補でも残っている（候補が無い場合を含む） |
| `unscannable` | ○ | ○ | 消えている候補が無く、スキャンできなかった候補がある |
| `pending` | ○ | ○ | 消えている候補が無く、まだスキャンしていない候補がある |

本番が直った版になれば、その発見は動いている版から消えるので、段階ごと無くなる。

`unscannable` になるのは、資格の無い private のレジストリ（registry.fraction.jp）、スキャンの失敗、
レジストリが読めないときである。レジストリが読めず候補そのものが見つからない場合も
`unscannable` とする（候補が無いのか、読めなかったのかを区別する）。

### 修正版が無いもの

VulnerabilityReport の `fixedVersion` が空の脆弱性（2026-10-27 時点で 2,293 / 3,908）も、
同じ規則で段階を決める。修正版が無くても、上流が新しい版でパッケージを外したり入れ替えたり
して消えることがあるからである。修正版の有無は段階とは別に `fixable` として出し、
即時のアラートは `fixable` のものだけにする（ADR 0005）。

### Renovate の PR

fleet-infra と k8s-manifests-fraction の、Renovate が出した開いている PR を読み、
タイトルか本文にイメージの名前があるものを、そのイメージの補足として出す（段階は変えない）。

### fleet-infra の対応表

ラベルの無いイメージのソースと、系列の上書きは、fleet-infra の
`security/image-sources.yaml` に置くことを提案する（ファイルの形は fleet-infra 側の作業単位で決め、
README に書く）。1 項目は、イメージの名前（`<registry>/<repository>`）、ソースの URL（任意）、
系列のタグの正規表現（任意）である。ファイルが無ければ、表は空として扱う。

### 読む間隔

| 読むもの | 間隔 | 備考 |
|---|---|---|
| VulnerabilityReport・Pod | watch | |
| fleet-infra・k8s-manifests-fraction | 10 分ごとに既定ブランチの HEAD を確かめ、変わったときだけ中身を取る | VEX もここから読む |
| レジストリのタグ一覧 | 6 時間ごと | Docker Hub の匿名の rate limit を避ける |
| `:main` などの動くタグの digest | 1 時間ごと | HEAD で読む |
| イメージのラベル | digest が変わったとき | |
| 候補のスキャン | 同じ digest は 24 時間に 1 回 | 脆弱性 DB の更新を拾う |

## Consequences

- 判定はすべて「その版を実際にスキャンして消えたか」で決まる。ラベルの revision や GitHub の
  タグとコミットの前後関係から推測しないので、ベースイメージの更新で消えた場合も、
  依存の更新で消えた場合も、同じように扱える
- 候補のスキャンにはクラスタの資源とレジストリへの読みがかかる。1 つのイメージにつき候補は
  最大 3 つで、digest で重複を除くので、1 日のスキャンはおおむね 100 本前後に収まる見込みである
- git の中の書き方が上の形でないと、`in-git` を見落とす。見落とした発見は 1 つ手前の段階に留まる
- 外のイメージの系列は、タグの付け方が素直でないもの（日付やコミットのハッシュを含むタグなど）で
  候補が見つからない。対応表で正規表現を与えるまで `unfixed` に見える
- ソースが分からないことは段階にしない。段階の判定はソースが無くてもできるからである
