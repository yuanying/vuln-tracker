# 0014. 対応の進み具合を、ソース側とマニフェスト側の 2 軸で持ち、PR を結び付ける

- Date: 2026-10-29
- Status: Accepted

## Context

段階（ADR 0002）は、発見ごとに「脆弱性が消えている最も先の候補」で 1 つだけ決まる。
ソース側（自作の `:main`・リリース）とマニフェスト側（git に書かれた版・本番）の進み具合が
1 つの値に畳まれるので、たとえば「リリースは出たが fleet-infra の版上げがまだ」と
「main で直ったがリリースがまだ」が、段階を見ただけでは並べて読めない。

また、集計役は PR をほとんど見ていない。マニフェストのリポジトリの、イメージ名が書かれた
Renovate の PR を補足として出すだけで、自作のソースのリポジトリの PR は読まない。
vuln-responder の返事の PR の URL は target ごとに状態に持つが、開いているかマージ済みかは見ない。

ユーザーは、発見ごとに 2 軸の状態と、結び付いた PR を、pi の codemode のツールから読みたい
（出口は ADR 0015 の JSON の API）。

## Decision

### 判定の原則

2 軸の状態も、段階と同じく **候補の版のスキャン** で決める（ADR 0002）。PR は「直すつもり」の印であり、
直ったことの証明にはしない。PR が効くのは「未対応」と「PR が上がっている」の区別だけである。
2 軸は段階と同じスキャンの結果から計算するので、段階・メトリクス・ダイジェスト・依頼は変わらない。

### ソース側（`source.state`）

自作のイメージだけが持つ。上から順に、最初に当てはまるものにする。

| 状態 | 判断のしかた |
|---|---|
| `unknown` | discovery がまだその版に届いていない（自作かどうかも分からない） |
| `not-applicable` | 自作でないイメージ |
| `released` | 最新のリリースの候補（`release`）をスキャンして、消えている |
| `merged` | `:main` の候補をスキャンして、消えている（段階の `fixed-in-main`） |
| `unknown` | `main`・`release` の候補にまだスキャンしていないか、スキャンできなかったものがある。またはレジストリが読めなかった |
| `pr-open` | ソースのリポジトリに、結び付いた開いている PR がある |
| `unaddressed` | 上のどれでもない（候補が無い場合を含む） |

- `:main` がリリースと同じコミットから作られていて候補から省いたとき（ADR 0002）は、リリースの結果がそのまま答えになる
- git の候補はソース側に数えない
- 消えたことが確かめられたら、他の候補が未スキャンでも `merged`・`released` にする（消えた証拠が先に立つ）。
  逆に「消えていない」ことは全部の候補を見るまで言えないので、未スキャンが残るうちは `unknown` にする。
  PR が開いていても `unknown` が先に立つ（PR は `pullRequests` に並ぶ）

### マニフェスト側（`manifest.state`）

自作・外のイメージに共通。fleet-infra と k8s-manifests-fraction（`--manifests`）を同じに扱う。
上から順に、最初に当てはまるものにする。

| 状態 | 判断のしかた |
|---|---|
| `unknown` | discovery がまだその版に届いていない |
| `merged` | git に書かれた版の候補（`git`）のどれかをスキャンして、消えている（段階の `in-git`）。本番への apply 待ち |
| `unknown` | `git` の候補にまだスキャンしていないか、スキャンできなかったものがある |
| `pr-open` | **直った版がある**、かつマニフェストのリポジトリに結び付いた開いている PR がある |
| `unaddressed` | **直った版がある** が、結び付いた開いている PR が無い |
| `unknown` | 直った版の候補にまだスキャンしていないか、スキャンできなかったものがある。またはレジストリが読めなかった |
| `no-fix` | 上のどれでもない。直った版がまだ無い（候補が無い場合を含む） |

- **直った版** とは、自作ならリリースの候補（`release`）、外なら上流の同じ系列の候補（`upstream`）をスキャンして、
  脆弱性が消えているものである。自作の `:main` だけで消えているものは、版上げの先がまだ無いので `no-fix` にする
  （ソース側は `merged`）
- 「リリースされている（本番で消えた）」は、発見そのものが消えるので値に無い（ADR 0002）
- `no-fix` と `unknown` の境目: 候補が 1 つも無い（上流がまだ新しい版を出していない、自作のリリースが動いている版のまま）ときは
  `no-fix`。候補はあるがまだスキャンしていない・スキャンできない・レジストリが読めず候補があるかも分からないときは `unknown`
- 直った版の候補がまだ未スキャンでも、開いている PR だけでは `pr-open` にしない。その PR が直る版を指しているかは、
  スキャンするまで分からないからである
- `manifest.repository` は、`--manifests` の順に見て、最初にそのイメージの版を書いているリポジトリ（`owner/name`）。
  どれにも書かれていなければ空

### 候補の重複

ADR 0002 のとおり、候補は digest で同一視してスキャンを 1 回で済ませる。ただし、git に書かれた版が
リリースや上流の候補と同じ digest のとき（版上げの PR がマージされた直後はたいていそうなる）でも、
`git` の候補は省かない。省くと `in-git` と `manifest.state` の `merged` に届かないからである。
候補は種類ごとに 1 つずつ持ち、スキャンは digest ごとに 1 回のままにする。

### PR の結び付け

結び付ける理由（`link`）は次の 3 つ。1 つの PR は 1 つの理由で 1 回だけ結び付け、優先は上から。

| `link` | 対象 | 条件 |
|---|---|---|
| `vuln-responder` | 返事の PR が属するリポジトリ | その発見を含む依頼（`asked`・送り中の発見）に vuln-responder が返した PR。状態（open・merged・closed）を問わない |
| `renovate` | ソースのリポジトリ | 作者が `--renovate-author` に当たり、タイトルか本文に **パッケージ名** が 1 語として書かれている開いている PR |
| `renovate` | マニフェストのリポジトリ | 作者が `--renovate-author` に当たり、タイトルか本文に **イメージ名** が 1 語として書かれている開いている PR（ADR 0002 の補足と同じ規則） |
| `mentions-id` | ソースとマニフェストのリポジトリ | タイトルか本文に **脆弱性の ID**（`CVE-…`・`GHSA-…` など、VulnerabilityReport の ID そのまま）が書かれている開いている PR。大文字小文字は区別しない |

- 語の切れ目: イメージ名・パッケージ名は英数字と `-` `_` `/` `.` の続きを 1 語とする（`nginx` は `nginx-exporter` に当たらない）。
  脆弱性の ID は英数字と `-` の続きを 1 語とする（文末の `.` で切れ、`CVE-2026-1` は `CVE-2026-12` に当たらない）
- どの軸に入るかは PR のリポジトリで決める。発見のソースのリポジトリならソース側、`--manifests` のリポジトリならマニフェスト側。
  どちらでもないリポジトリの PR は結び付けない
- **VEX だけを変える PR**（変更したファイルがすべて `security/vex/` の下にある、マニフェストのリポジトリの PR）は、
  直すものではなく注釈なので、どちらの軸にも入れず、注釈の側（API の `vex.pullRequests`）に並べる。
  vuln-responder は `vex-only` の mode では fleet-infra に VEX の PR を出す（ADR 0009）ので、これをマニフェスト側の
  `pr-open` に数えると、注釈しただけの発見がすべて「PR が上がっている」に見えてしまう。
  ファイルを読むのは、マニフェストのリポジトリの、Renovate でない開いている PR と、vuln-responder の返事の PR だけである
- Renovate の PR は、本文にリポジトリの依存の一覧などを書くので、イメージ名やパッケージ名を書いた PR は、その版上げで
  その脆弱性が消えるかにかかわらず、そのイメージ（パッケージ）のすべての発見に結び付く。消えたかどうかはスキャンが決める

#### ソースのリポジトリの Renovate の PR をパッケージ名で結び付ける

結び付ける。自作のイメージの脆弱性の多くは、Go のモジュールや gem・npm の依存であり、Renovate の PR は
タイトルにその名前（`Update module golang.org/x/net to v0.33.0`、`Update dependency json to v2.18.1`）をそのまま書く。
Trivy のパッケージ名も同じ名前なので、1 語として照らせば十分に当たる。

当たらないものもある。ベースイメージの版上げ（`Update ruby Docker tag`）で消える OS のパッケージ、Go の標準ライブラリ
（Trivy は `stdlib`、Renovate は `go` の版）である。これらは PR が結び付かず `unaddressed` に見えるが、
直ればスキャンで `merged` になる。人が出す PR に脆弱性の ID を書けば `mentions-id` で結び付く。

逆に、短い一般的な名前（`json` など）は、別のパッケージの PR の本文に 1 語として現れることがありうる。
作者を Renovate に絞り、PR がそのソースのリポジトリのものに限られるので、誤りは小さいと見る。

### 読み方と間隔

すべて GitHub の REST API で読む。search API は使わない（1 分 30 回と別の上限があり、索引の遅れもある）。
リポジトリごとに開いている PR の一覧を読み、手元で照らす。

| 読むもの | API | 間隔 |
|---|---|---|
| マニフェストのリポジトリの HEAD・中身・開いている PR | 既存（ADR 0002・0007） | `--git-interval`（既定 10 分） |
| 自作のイメージのソースのリポジトリの開いている PR | `GET /repos/{repo}/pulls?state=open&per_page=100`（1 ページ） | `--git-interval`。discovery の後に、動いている自作のイメージのソース（ラベル）から集める |
| vuln-responder の返事の PR の状態 | `GET /repos/{repo}/pulls/{number}` | `--git-interval`。merged になったものは読み直さない |
| VEX だけを変える PR かどうか | `GET /repos/{repo}/pulls/{number}/files?per_page=100`（1 ページ） | head の commit が変わったときだけ |

読めなかったものは前に読めた中身で続け、`vuln_tracker_sync_errors_total{target="pull-requests"}` に数える
（ADR 0005 の追記）。

### rate limit の見積もり

GitHub App の installation は 1 時間 5,000 回（ADR 0013）。2026-10-29 の数で見積もる。
マニフェストのリポジトリが 2、自作のイメージのソースのリポジトリが 13、vuln-responder の target がおおむね 20 以下である。

| 読むもの | 10 分ごとの回数 | 1 時間 |
|---|---|---|
| マニフェストの HEAD と開いている PR | 2 × 2 = 4 | 24 |
| マニフェストの tarball | HEAD が変わったときだけ（多くて 1） | 6 以下 |
| ソースのリポジトリの開いている PR | 13 | 78 |
| 返事の PR の状態 | merged でないもの、20 以下 | 120 以下 |
| PR のファイル | 新しい head のものだけ（数件） | 30 以下 |
| 合計 | | **260 以下** |

上限の 5% ほどである。ソースのリポジトリが 50 に増えても 500 前後に収まる。
App を作る前に `GITHUB_TOKEN` の PAT で動かす場合も、PAT の上限は 1 時間 5,000 回なので足りる
（ただし PAT の対象に入っていない private のソースのリポジトリは読めず、`pull-requests` のエラーに数える）。
資格なし（匿名、1 時間 60 回）では、ソースのリポジトリを読むだけで上限を超えるので、資格を置くこと。

### メトリクス

2 軸はメトリクスには出さない。出口は ADR 0015 の JSON の API である。ADR 0005 の系列とラベル（`stage` を含む）は変えない。

## Consequences

- 段階（1 軸）と 2 軸は同じスキャンから出るので、食い違わない。段階が `in-git` なら `manifest.state` は `merged`、
  `fixed-in-main` ならソース側は `merged` である
- PR の結び付けは文字の照合なので、PR に名前や ID を書かない直し方は結び付かない。状態は `unaddressed` に見えても、
  直ればスキャンで進む
- 返事の PR は target ごとに最後の 1 つしか状態に持たない（ADR 0009）。同じ target への前の依頼の PR は結び付かない
- ソースのリポジトリの開いている PR を 100 件まで、PR のファイルを 100 件までしか読まない。それを超えるリポジトリ・PR は無い前提である
- GitHub の読みが 1 回の同期で 20 回ほど増える
